# ACTIVIDAD ACADÉMICA — APLICANDO SQA EN NUESTRAS HISTORIAS DE USUARIO

Actúa como un ingeniero de aseguramiento de la calidad de software (SQA), analista de requisitos y especialista en documentación técnica de proyectos Laravel.

Ya existe un sistema web llamado **StockFácil**, desarrollado con Laravel, Blade, Tailwind CSS y una base de datos local SQLite.

El sistema ya fue implementado. Ahora necesito que revises el código y prepares todos los entregables de una actividad universitaria titulada:

**“Aplicando SQA en nuestras historias de usuario”**

IMPORTANTE: Esta actividad es sobre un proyecto REAL y ya desarrollado.

NO debes crear otro proyecto ni reemplazar el sistema existente.

Debes trabajar directamente sobre el repositorio actual, analizar su implementación, comprobar sus funcionalidades y generar documentos académicos completos basados en evidencia verificable.

# 1. INSTRUCCIONES ORIGINALES DE LA TAREA

La actividad se divide en dos fases.

## FASE 1 — SELECCIÓN Y PREPARACIÓN

Cada equipo debe seleccionar una o dos historias de usuario de su proyecto actual.

Para cada historia se debe definir:

- Criterios de aceptación.
- Artefactos relacionados: mockups, casos de uso, código y documentación técnica.

## FASE 2 — APLICACIÓN DE ACTIVIDADES SQA

Cada equipo debe aplicar tres tipos de control:

### A. REVISIÓN

Descripción:

Revisión técnica de requisitos o diseño por parte de otro equipo.

Evidencia esperada:

Lista de verificación con observaciones y mejoras.

### B. INSPECCIÓN

Descripción:

Evaluación formal de código o documentación técnica por pares, utilizando una lista de control SQA.

Evidencia esperada:

Acta de inspección que incluya participantes, hallazgos y acciones correctivas.

### C. AUDITORÍA SQA

Descripción:

Revisión independiente por el docente o un equipo designado para verificar la conformidad con el plan de calidad o los estándares del curso.

Evidencia esperada:

Informe de auditoría con grado de cumplimiento expresado en porcentaje y recomendaciones.

# 2. PRODUCTO FINAL QUE EXIGE LA TAREA

Se debe entregar un INFORME SQA POR HISTORIA DE USUARIO.

Cada informe debe contener obligatoriamente:

1. Descripción breve de la historia de usuario.
2. Evidencia de revisión: lista de hallazgos y acciones.
3. Evidencia de inspección: capturas, checklist y observaciones.
4. Resultado de la auditoría: cumplimiento y conclusiones.

Como trabajaremos con dos historias de usuario, debemos generar dos informes completos.

Además, elabora un informe general que reúna ambos resultados.

# 3. HISTORIAS DE USUARIO SELECCIONADAS

Utiliza las siguientes historias de usuario del proyecto StockFácil.

## HISTORIA DE USUARIO 01 — REGISTRO DE PRODUCTOS

Identificador: HU-01

Título: Registro de productos.

Descripción:

Como administrador de una tienda, quiero registrar nuevos productos con su información correspondiente para mantener actualizado el inventario de mi negocio.

Criterios de aceptación:

CA-01: El sistema debe exigir el nombre del producto.

CA-02: El SKU o código del producto debe ser único.

CA-03: El precio no puede ser negativo.

CA-04: La cantidad inicial no puede ser negativa.

CA-05: Cuando se registre correctamente un producto, este debe aparecer en el inventario.

CA-06: Cuando se ingresen datos inválidos, el sistema debe mostrar mensajes de validación.

## HISTORIA DE USUARIO 02 — CONTROL DE EXISTENCIAS

Identificador: HU-02

Título: Control de entradas y salidas de inventario.

Descripción:

Como administrador de una tienda, quiero registrar las entradas y salidas de productos para controlar las cantidades disponibles en mi inventario.

Criterios de aceptación:

CA-01: Las entradas deben incrementar correctamente las existencias.

CA-02: Las salidas deben disminuir correctamente las existencias.

CA-03: No se debe permitir retirar más productos de los disponibles.

CA-04: No se deben permitir movimientos con cantidades iguales o menores a cero.

CA-05: Cada entrada y salida debe quedar registrada en el historial.

CA-06: El sistema debe mostrar alertas cuando un producto alcance su stock mínimo.

IMPORTANTE:

Estos criterios provienen de la planificación del proyecto.

Debes comprobar que realmente coincidan con la implementación.

Si existe una diferencia entre lo planificado y lo desarrollado, documenta la discrepancia como hallazgo, sin modificar arbitrariamente los criterios originales.

# 6. FASE 2 — ACTIVIDAD SQA N.º 1: REVISIÓN

Debes preparar una revisión técnica de requisitos y diseño para ambas historias.

## Lista de verificación

Crea una checklist con al menos los siguientes aspectos:

1. La historia de usuario tiene una descripción clara.
2. El actor está correctamente identificado.
3. El objetivo de la historia es comprensible.
4. Los criterios de aceptación están definidos.
5. Los criterios son verificables.
6. No existen contradicciones entre requisitos.
7. El diseño corresponde a la funcionalidad solicitada.
8. Los formularios contienen los campos necesarios.
9. Se contemplan validaciones de datos.
10. Se contemplan mensajes de error.
11. El flujo de uso es coherente.
12. La historia tiene artefactos técnicos identificables.

Utiliza una tabla con estas columnas:

- N.º
- Aspecto evaluado
- Resultado (Cumple / No cumple / No aplica / No verificado)
- Observación
- Acción de mejora
- Referencia de evidencia

Analiza realmente el proyecto.

No marques todos los puntos como satisfactorios sin comprobarlos.

IMPORTANTE:

Deja campos para:

- Firma o validación.
- Observaciones adicionales del equipo externo.

Identifica claramente cuáles resultados provienen de la evaluación técnica automatizada y cuáles están pendientes de revisión por otro equipo.

# 9. ACTIVIDAD SQA N.º 3: AUDITORÍA

Prepara la documentación necesaria para una auditoría SQA de ambas historias.

La auditoría debe evaluar la conformidad con los criterios de aceptación definidos y los estándares de calidad del proyecto.

Como todavía no se ha confirmado una auditoría independiente por parte del docente o equipo designado, debes elaborar una **preevaluación técnica de cumplimiento** y dejar preparado el informe para su posterior validación independiente.

No presentes la evaluación de Codex como si fuera una auditoría oficial realizada por el docente.

## Matriz de cumplimiento

Para cada historia, evalúa sus seis criterios de aceptación.

Utiliza las columnas:

- Código del criterio.
- Descripción.
- Evidencia objetiva.
- Resultado.
- Observación.
- Recomendación.

Usa estos estados:

- Cumple.
- No cumple.
- No verificado.
- No aplica, solo cuando esté debidamente justificado.

## Cálculo del cumplimiento

Calcula el cumplimiento verificado mediante:

Cumplimiento (%) = (Criterios comprobados que cumplen / Total de criterios aplicables) × 100

Consideraciones:

- Un criterio no verificado no puede contarse como cumplido.
- Los criterios no aplicables solo se excluyen si existe una justificación.
- Presenta además el número de criterios no verificados.
- Si existen pruebas bloqueadas, explícitalo en el informe.
- No utilices resultados supuestos para elevar el porcentaje.

Incluye un ejemplo numérico únicamente si corresponde a resultados reales.

Genera:

1. Porcentaje técnico de cumplimiento de HU-01.
2. Porcentaje técnico de cumplimiento de HU-02.
3. Porcentaje técnico global del proyecto para los criterios evaluados.

No promedies porcentajes sin considerar el número de criterios aplicables.

Identifica todos estos valores como resultados de la preevaluación técnica, pendientes de validación oficial.

## Informe de auditoría

Dejar campos para:

- Observaciones oficiales.
- Resultado aprobado por el auditor.
- Firma o validación.
